# 一、请求方法

## 1.1 五个方法

| 方法 | 语义 | 类比 | 幂等 |
|---|---|---|---|
| **GET** | 查询，只读不改 | 看菜单 | ✅ |
| **POST** | 新增 | 点一道新菜（每次都多一道） | ❌ |
| **PUT** | **全量**替换/更新 | 换掉整份菜单 | ✅ |
| **PATCH** | **局部**更新 | 只改一道菜的价格 | ❌ |
| **DELETE** | 删除 | 划掉一道菜 | ✅ |

## 1.2 PUT vs PATCH（重要）

原始数据：

```json
{"userId": 1, "userName": "admin", "status": "0", "email": "a@b.com"}
```

### PATCH（局部更新）

请求体：

```json
{"status": "1"}
```

结果：**只有 status 变了，email 保留** ✅

### PUT（全量替换）

请求体：

```json
{"userName": "admin", "status": "1"}
```

结果：**email 被清空** ⚠️

> **PUT 的坑：没传的字段 = 要清空，不是保持不变。**
>
> **测试价值**：专门用 PUT 故意少传字段，看会不会把数据搞丢。这是很容易发现真实 Bug 的地方。

## 1.3 幂等性（面试必考）

> **幂等 = 同一请求执行 1 次和 100 次，服务器最终状态相同。**

| 方法 | 幂等 | 原因 |
|---|---|---|
| GET | ✅ | 查多少次数据都不变 |
| PUT | ✅ | 全量覆盖，改 100 次结果一样 |
| DELETE | ✅ | 删完再删，结果都是"没了" |
| **POST** | ❌ | 每发一次**多一条记录** |
| **PATCH** | ❌ | 若是"库存 +1"，发 5 次就 +5 |

### 生活化理解

- **GET** = 看价目表（看一次和看十次没区别）
- **PUT** = 整张价目表换成新的（换一次和换十次，最后都是新的）
- **POST** = 下单买菜（下一次一单，下十次十单）
- **DELETE** = 取消订单（取消几次都是取消）
- **PATCH** = 购物车再加一个（加十次就多十个）

### 为什么测试要关心

典型 Bug 场景：

```
用户在支付页手抖点了两下"支付"
→ 前端发了两次 POST
→ 后端生成两笔订单
→ 用户被扣两次钱        ← P0/P1 级 Bug
```

**测试方法**：
1. 用同一请求连发 5 次（Postman Collection Runner / 代码循环）
2. 查数据库是否真的插入 5 条
3. 检查后端是否有防重（唯一约束 / 幂等 token / 分布式锁）

## 1.4 GET vs POST 完整对比

| 维度 | GET | POST |
|---|---|---|
| 语义 | 查询 | 提交/新增 |
| 参数位置 | URL（`?a=1&b=2`） | 请求体 body |
| 长度限制 | 有（约 2K–8K） | 理论上无 |
| 可缓存 | ✅ | ❌ |
| 幂等 | ✅ | ❌ |
| 是否修改数据 | ❌ | ✅ |
| 参数进日志/浏览器历史 | ✅（**所以别用 GET 传密码**） | ❌ |
| 传文件 | ❌ | ✅（multipart） |

# 二、状态码

## 2.1 五个大类

| 开头 | 含义 | 谁的问题 |
|---|---|---|
| **2xx** | 成功 | — |
| **3xx** | 重定向 | — |
| **4xx** | 客户端错误 | **我的请求有问题** |
| **5xx** | 服务端错误 | **开发的 Bug** |

> **核心判断：4xx 是我传错了，5xx 是服务器崩了。**

## 2.2 必背 11 个状态码

### 2xx 成功

| 码 | 名称 | 含义 | 典型场景 | 测试时怎么判断 |
|---|---|---|---|---|
| **200** | OK | 成功 | 查询/更新成功 | **还要看业务 code**，很多系统 HTTP 200 但业务失败 |
| **201** | Created | 创建成功 | POST 新增资源 | 新增接口按文档判断是 200 还是 201 |
| **204** | No Content | 成功但无返回体 | DELETE / PUT | **不要 `resp.json()`**，会抛 JSONDecodeError |

### 3xx 重定向

| 码 | 名称 | 含义 | 典型场景 | 测试时怎么判断 |
|---|---|---|---|---|
| **301** | Moved Permanently | 永久重定向 | 域名变更、HTTP 强制跳 HTTPS | 接口测试基本不涉及 |
| 302 | Found | 临时重定向 | 登录后跳首页 | Postman 需关掉「自动跟随重定向」才能看到 |

### 4xx 客户端错误

| 码 | 名称 | 含义 | 典型场景 | 测试时怎么判断 |
|---|---|---|---|---|
| **400** | Bad Request | 参数错误 | 缺必填字段、类型错、长度超限 | **先检查自己的请求参数**，不是 Bug |
| **401** | Unauthorized | 未认证 | 没带 token / token 过期或伪造 | 检查 `Authorization` 头 |
| **403** | Forbidden | 无权限 | 普通角色访问管理员接口 | **权限设计问题**，登录是正常的 |
| **404** | Not Found | 资源不存在 | id 不存在、URL 拼错 | 检查 URL 路径和 id |
| **405** | Method Not Allowed | 方法不允许 | GET 接口用了 POST | 检查请求方法 |
| 415 | Unsupported Media Type | 媒体类型不支持 | Content-Type 设错 | 检查 Body 类型和 Content-Type |

### 5xx 服务端错误

| 码 | 名称 | 含义 | 典型场景 | 测试时怎么判断 |
|---|---|---|---|---|
| **500** | Internal Server Error | 服务器内部异常 | 代码抛未捕获异常、空指针 | **基本是 Bug，提缺陷** ⚠️ |
| **502** | Bad Gateway | 网关错误 | 后端服务没启动 / 重启中 | **环境问题，不是 Bug** |
| 503 | Service Unavailable | 服务不可用 | 过载 / 维护 | 看是否为压测场景 |
| 504 | Gateway Timeout | 网关超时 | 后端处理太慢 | 性能问题 |

## 2.3 三组易混状态码（重点）

### ① 401 vs 403

| | **401 Unauthorized** | **403 Forbidden** |
|---|---|---|
| 通俗说 | **"你是谁？我不认识你"** | **"我知道你是谁，但你不能干这事"** |
| 原因 | 没登录 / token 缺失、过期、伪造 | 已登录，但角色权限不足 |
| 解决 | 重新登录拿新 token | 找管理员加权限 |
| 怎么造 | 请求不带 `Authorization` 头 | 用普通账号调管理员接口 |

> **记忆口诀**
> **401 = 没带身份证，进不了大门**
> **403 = 带了身份证，但没权限进这个房间**

### ② 500 vs 502

| | **500** | **502** |
|---|---|---|
| 请求到哪了 | 到了应用，应用内部报错 | **卡在 Nginx，没到应用** |
| 原因 | 代码 Bug | 后端进程没起 / 挂了 |
| 定性 | **Bug，要提缺陷** | **环境问题，重启服务** |

> 起若依时如果页面报 502：**先看 Java 服务起没起**，不是测试脚本的问题。

### ③ HTTP 200 + 业务 code 500

很多国内系统（包括若依）**HTTP 状态码永远返回 200**，业务错误放在响应体：

```json
{"code": 500, "msg": "用户名已存在"}
```

**此时 HTTP 状态码是 200，但业务失败了。**

所以断言必须写两层：

```python
assert resp.status_code == 200          # HTTP 层
assert resp.json()["code"] == 200       # 业务层 ← 别漏
```

> **只断言 HTTP 200 会漏掉一半 Bug。**

# 三、请求头

## 3.1 Content-Type（测试最常踩的坑）

告诉服务器「我发过来的数据是什么格式」。

| 值 | 用途 | Postman 里怎么选 |
|---|---|---|
| `application/json` | 传 JSON（最常用） | Body → **raw → JSON** |
| `application/x-www-form-urlencoded` | 表单（`a=1&b=2`） | Body → **x-www-form-urlencoded** |
| `multipart/form-data` | 传文件/图片 | Body → **form-data** |

### 经典错误

```
Postman 选了 form-data，但服务器要 JSON
→ 返回 400 或 415
→ 以为是接口坏了，其实是自己 Body 类型选错
```

> **看到 400 / 415，第一件事检查 Content-Type。**

### 用 requests 时

```python
# ✅ 正确：json= 参数会自动设 Content-Type: application/json
requests.post(url, json={"a": 1})

# ❌ 错误：data= 传字符串会被当成表单
requests.post(url, data='{"a": 1}')
```

## 3.2 Authorization（身份凭证）

```
Authorization: Bearer eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...
```

- `Bearer` 后面跟 token
- 现代系统最常用
- **若依用的就是这个**：`Authorization: Bearer <token>`

另一种老式写法：

```
Authorization: Basic base64(用户名:密码)
```

## 3.3 Cookie（会话标识）

```
Cookie: JSESSIONID=ABC123DEF456
```

- 服务器发的「记住我是谁」的小纸条
- 浏览器自动带，**requests 需要手动处理**（用 `requests.Session()` 会自动管理）

## 3.4 Cookie vs Token（面试常问）

| | Cookie + Session | Token（JWT） |
|---|---|---|
| 状态存哪 | 服务器内存/数据库 | **客户端自己带** |
| 服务器有无状态 | ✅ 有状态 | ❌ 无状态 |
| 适合场景 | 单机、传统 Web | 分布式、前后端分离 |
| 缺点 | 集群需共享 Session | 注销难、token 体积大 |

# 四、RESTful 与 URL 设计

## 4.1 核心思想

> **URL 里只放「名词」（资源），「动词」交给 HTTP 方法。**

## 4.2 好 vs 坏对照

| ❌ 非 RESTful | ✅ RESTful | 说明 |
|---|---|---|
| `GET /getUserList` | `GET /users` | 查询列表 |
| `GET /getUserById?id=1` | `GET /users/1` | 查单个 |
| `POST /addUser` | `POST /users` | 新增 |
| `POST /updateUser` | `PUT /users/1` | 全量更新 |
| `POST /updateUserStatus` | `PATCH /users/1` | 局部更新 |
| `GET /deleteUser?id=1` | `DELETE /users/1` | 删除 |
| `GET /users/1/getRoles` | `GET /users/1/roles` | 查关联资源 |

## 4.3 三条设计规则

### ① 资源用复数名词

```
/users    ✅         /user    ❌
/orders   ✅         /order   ❌
```

### ② 层级表示归属关系

```
/users/1/roles        用户 1 的所有角色
/orders/100/items     订单 100 的所有商品
```

### ③ 过滤/分页/排序用查询参数

```
GET /users?status=0&pageNum=1&pageSize=10
```

不是：

```
GET /getUsersByStatusAndPage?status=0&page=1     ❌
```

## 4.4 为什么测试要懂这个

| 价值 | 说明 |
|---|---|
| 从 URL 推断方法 | 看到 `DELETE /users/1` 就知道不该用 GET 测 |
| 发现设计隐患 | `GET /deleteUser` 这种设计，爬虫/预加载可能误删数据 |
| 面试会问 | 「你怎么看 RESTful 风格」 |

# 五、接口测试中的实际应用

## 5.1 一个接口该测什么（维度清单）

拿到 `POST /system/user` 这个接口，按这 6 个维度设计用例：

| 维度 | 用例举例 |
|---|---|
| **参数** | 必填缺失 / 类型错误 / 长度超限 / 特殊字符 / 空值 |
| **业务逻辑** | 用户名重复 / 正常创建 / 数据边界 |
| **权限** | 不带 token(401) / 错误 token(401) / 普通角色(403) |
| **方法** | 用 GET 调这个接口 → 405 |
| **幂等** | 连发 5 次，检查是否重复插入 |
| **数据一致性** | 接口返回成功后查数据库确认写入 |

## 5.2 断言要写几层

```python
resp = requests.post(url, json=data, headers=headers)

# 第 1 层：HTTP 状态码
assert resp.status_code == 200

# 第 2 层：业务 code / msg
body = resp.json()
assert body["code"] == 200
assert body["msg"] == "操作成功"

# 第 3 层：数据内容
assert body["data"]["userName"] == "test01"

# 第 4 层：数据库落库校验（第 3 周会用到）
# SELECT * FROM sys_user WHERE user_name = 'test01'
```

## 5.3 常见"假 Bug"与"真 Bug"

| 现象 | 定性 | 怎么判断 |
|---|---|---|
| 400 | 假 Bug | 先看自己的参数和 Content-Type |
| 401 | 假 Bug | 看 token 是否过期/没带 |
| 403 | 真问题（权限设计） | 确认是权限而非登录问题 |
| 404 | 假 Bug | 先看 URL 拼写 |
| 405 | 假 Bug | 请求方法用错 |
| **500** | **真 Bug** | 服务器异常，提缺陷 |
| 502 | 环境问题 | 后端服务没起 |

# 六、面试题自测

<details>
<summary>点开看答案</summary>

### 1. GET 和 POST 的区别？

语义（查询 vs 提交）、参数位置（URL vs body）、长度限制（有限 vs 无限）、幂等（GET 幂等，POST 不幂等）、缓存（GET 可缓存）、安全性（GET 参数暴露在 URL/日志里）。

### 2. PUT 和 PATCH 的区别？

PUT 是**全量替换**（没传的字段会被清空），PATCH 是**局部更新**（只改传了的字段）。PUT 幂等，PATCH 一般不幂等。

### 3. 什么是幂等性？哪些方法幂等？

同一请求执行 1 次和 N 次，服务器最终状态相同。GET / PUT / DELETE 幂等，POST / PATCH 不幂等。

### 4. 401 和 403 的区别？

401 = 未认证（没登录/token 无效）；403 = 已认证但无权限。

### 5. 500 和 502 的区别？

500 是应用内部异常（Bug）；502 是网关连不上后端（环境问题，后端没起）。

### 6. HTTP 状态码返回 200 就说明接口正常吗？

不是。很多系统 HTTP 200 但业务 code 是 500（把错误放在响应体），必须同时断言业务 code。

### 7. 怎么测试一个接口的幂等性？

用同一个"新增"请求连续发送多次，检查数据库是否产生重复记录；再检查后端是否有唯一约束、幂等 token、分布式锁等防重机制。

### 8. 接口测试中 Content-Type 设错会出现什么现象？

一般是 400 或 415。例如服务端要 `application/json`，前端发了 `form-data`，服务端解析不到参数。

### 9. 什么样的 URL 是 RESTful 的？

名词复数、层级表示关系、过滤用查询参数、动词交给 HTTP 方法。例如 `GET /users/1/roles` 而不是 `GET /getUserRoles?id=1`。

### 10. 接口返回 404，应该提 Bug 吗？

先排除自己 URL 写错、id 不存在。确认 URL 正确且资源确实存在时报 404，才是 Bug。

# 附：常用速查

## 状态码 → 该怎么办

```
200/201/204  → 成功，继续断言业务层
301/302      → 重定向，通常不用管
400          → 我的参数错了
401          → 我没登录 / token 无效
403          → 我权限不够
404          → URL 或 id 错了
405          → 请求方法错了
415          → Content-Type 错了
500          → 服务器 Bug，提缺陷
502/503/504  → 环境/服务问题，先确认服务是否在跑
```

## 一个接口的测试思路模板

```
1. 正向：正确参数 → 期望成功（同时验证数据库）
2. 必填：逐个删掉必填字段 → 期望 400 / 业务错误码
3. 类型：传错误类型 → 期望校验失败
4. 边界：最短/最长/0/负数
5. 特殊字符：引号、SQL 注入串、emoji、超长
6. 权限：不带 token / 错 token / 低权限角色
7. 方法：用错误的 HTTP 方法 → 405
8. 幂等：重复提交 → 检查是否重复入库
9. 关联：依赖其他接口的数据时，缺失依赖会怎样
```
