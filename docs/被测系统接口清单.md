## 三、数据结构

### 列表项 / 单项响应的标准形态

```json
{
  "id": "1",
  "name": "Google Pixel 6 Pro",
  "data": {
    "color": "Cloudy White",
    "capacity": "128 GB"
  }
}
```

**注意三件事**：

1. **`id` 是字符串** `"1"`，不是数字 `1` —— 断言时别写成 `== 1`
2. **`data` 是嵌套字典** —— 取值要 `resp.json()["data"]["color"]`
3. **`data` 可能是 `null`** —— 第 2 条数据就是 `"data": null`（详见下）

### ⚠️ 关键数据特征：`data` 可能为 null

```json
{
  "id": "2",
  "name": "Apple iPhone 12 Mini, 256GB, Blue",
  "data": null
}
```

**这条数据是天然的测试宝藏**：

```python
body = resp.json()

# ❌ 会崩：TypeError: 'NoneType' object is not subscriptable
color = body["data"]["color"]

# ✅ 正确：链式兜底
color = body.get("data") or {}
color.get("color", "无颜色信息")
```

> 这正好对应「接口返回字段缺失/为空」这一经典测试场景。
> **别把它当麻烦，当成现成的 Bug 演练素材。**

## 四、测试关注点（按接口）

### GET /objects

| 关注点 | 用例 |
|---|---|
| 状态码 | 200 |
| 返回类型 | 是数组 |
| 数量 | ≥ 13 |
| 元素结构 | 每个元素都有 `id` 字段 |
| 响应时间 | < 2000 ms（记下基准值） |

### GET /objects/{id}

| 关注点 | 用例 |
|---|---|
| 正常 id | 返回对应记录，`id` 与请求一致 |
| 不存在的 id（如 99999） | 期望 404 或业务错误，**不能 500** |
| 非法 id（如 `abc`） | 期望 400，**不能 500** |
| id 为空（`/objects/`） | 是否等价于列表接口 |

### POST /objects

| 关注点 | 用例 |
|---|---|
| 正常创建 | 返回新记录，含 `id` 和 `createdAt` |
| 缺 `name` | 期望 400 |
| 缺 `data` | 是否允许为 null |
| `data` 传非字典（如字符串） | 期望 400，不能 500 |
| 超长 `name`（1000 字符） | 期望 400 或正常创建（看设计） |
| **重复提交同一请求 3 次** | 是否生成 3 条（**验幂等性**） |

### PUT /objects/{id}

| 关注点 | 用例 |
|---|---|
| 全量更新 | 传 `name` + `data`，都生效 |
| **少传 `data`** | **原 `data` 是被清空还是保留？← 必测** |
| 不存在的 id | 期望 404 |
| 用 PATCH 的语法调 PUT | 看是否报错 |

### PATCH /objects/{id}

| 关注点 | 用例 |
|---|---|
| 只改 `name` | `data` 应保持不变 |
| 只改 `data.color` | 其它字段不变 |
| 传空 body `{}` | 期望 400 或 200（无变化），**不能 500** |

### DELETE /objects/{id}

| 关注点 | 用例 |
|---|---|
| 正常删除 | 200 / 204，随后 GET 该 id 应 404 |
| 重复删除同一 id | 第二次应 404，**不能 500** |
| 不存在的 id | 404 |
| 返回 204 时的处理 | **不要 `resp.json()`**，会抛 JSONDecodeError |

## 五、待实测确认项（明天写代码时验证）

| # | 待确认 | 怎么确认 |
|---|---|---|
| 1 | POST 成功返回 200 还是 201 | 发一次看状态码 |
| 2 | POST 响应体是否含 `createdAt` | 看响应 JSON |
| 3 | DELETE 返回 200 还是 204 | 发一次看状态码 |
| 4 | GET 不存在的 id 返回 404 还是 200+空 | 请求 `/objects/99999` |
| 5 | PUT 少传字段是否清空原值 | 先 PUT 完整数据，再 PUT 部分数据，GET 回来对比 |
| 6 | 非法 id 是否触发 500 | 请求 `/objects/abc` |

> **把这 6 项填成实测结果，你的接口清单就从「抄文档」变成「自己验证过的」。**
> 面试时这份东西比任何描述都有说服力。

## 七、转自动化时的对应关系

| Postman 手工 | Python + pytest 自动化 |
|---|---|
| GET `{{baseUrl}}/objects` | `client.get("/objects")` |
| Tests 里 `pm.response.to.have.status(200)` | `assert resp.status_code == 200` |
| `pm.response.json().length` | `len(resp.json())` |
| `pm.expect(...).to.eql("x")` | `assert ... == "x"` |
| Environment 变量 | `config.yaml` + fixture |
| 手动点 Send | `pytest` 一条命令跑全部 |
